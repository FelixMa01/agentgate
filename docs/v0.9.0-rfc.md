# v0.9.0 RFC

> Status: **draft** — open for feedback via GitHub issues / discussions.
> Target: late 2026 / early 2027.
> Maintainer: @FelixMa01

## Goal

Pick the next 2-3 items from the deferred backlog and ship them as v0.9.0. The bar is
the same as v0.8.0: works on Linux / macOS / Windows, ≥80% test coverage for new code,
PyPI + GitHub Release, docs.

## Candidates

### 1. WASM plugin runtime — **P2 (optional)**

Allow users to write policy actions in Rust → compile to `.wasm` → load at runtime.
Closes the gap where today every adapter lives in the core Python repo.

**Why defer:**
- Plugin authoring is a UX design problem (manifest format, error messages, sandboxing
  boundaries) that we don't have bandwidth to nail yet.
- mitmproxy already has a Python plugin API — WASM only matters if users want a non-Python
  stack. Zero evidence of that demand today.

**Trigger to bump to P1:** GitHub issue or discussion with ≥3 👍 saying they want to
write policy logic in Rust / Go / TypeScript.

### 2. gRPC for hosted push-events — **P2 (optional)**

Today hosted team mode polls (`agentgate hosted pull-policy`). Replace with gRPC
streaming so the host daemon pushes policy updates as soon as they're committed.

**Why defer:**
- Polling at 30s interval works fine for a team of <20 developers.
- gRPC adds a protobuf schema, generated stubs in 3 languages, and a new failure
  mode (connection drops, retries, ordering). Not worth the maintenance cost at our
  current scale.

**Trigger to bump to P1:** First paying hosted-team customer, or ≥10-team adoption.

### 3. Cross-host audit DB sync — **P1 (likely)**

Users run AgentGate on multiple machines (dev laptop + work server). They want
events from both in one dashboard. Today each host has its own SQLite file.

**Options under consideration:**
- **a) Plain file copy over SSH** — simplest. `agentgate audit-sync user@host:/path/to/audit.db`. Brings down the local dashboard with merged data.
- **b) Central SQLite server** — every host writes to a shared Postgres. Requires running a server.
- **c) CRDT-based merge** — embed a CRDT in each event row, merge from multiple sources. Most robust, most complex.

**Recommendation:** start with **a)** — covers 80% of the use case in 100 lines of code.
Add **b)** if users complain about manual sync. Skip **c)** until option **a)** is
proven insufficient.

### 4. Web dashboard v2 — **P3 (later)**

The current HTML dashboard is single-page, single-user. A v2 would add:
- multi-host aggregation (depends on cross-host sync landing first)
- filtering by time range + rule + source (we have `--by-source/--by-rule` in CLI; just need to expose in UI)
- export to CSV

### 5. WASM sandboxing — **P3**

If WASM plugins land, also add a permission model (which files / domains each plugin
can touch).

Reply on the linked discussion (or open a new issue) with 👍 on the candidate you

## Out of scope for v0.9.0

These came up but we're explicitly NOT doing them:

- **Cloud-hosted AgentGate SaaS** — too much operational weight for one maintainer.
- **Agent-specific fine-tuning of policies** — too speculative.
- **Multi-tenant hosted mode** — security model is unclear.

## Open questions

- Should v0.9.0 be a minor bump or skip to v1.0.0? Argument for v1.0.0: cross-host
  sync + alerts feels like a "production-ready" milestone. Counter: we haven't
  promised API stability yet, and forcing v1 commitments too early is the same
  mistake every JS framework made in 2015.
- What's the CI matrix for v0.9.0? Currently ubuntu + macOS + Windows × 3.12 + 3.13.
  Adding 3.14? Beta? Skip.

- v0.8.0 has 1 star, 0 open issues (after closing #1), 91 tests passing, CI on 3 OSes.
- Real adoption signal: zero. If by mid-2027 we still have no production users,
  consider archiving the repo and pointing people at mitmproxy + a custom adapter.
